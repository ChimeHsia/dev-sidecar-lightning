# GitHub 连接超时修复（2026-11-05）

## 定位

浏览器 `DshaAccel` 当前启动的仍是 Node Sidecar；Kotlin 原生网络 runtime
没有接管浏览器。部分规则、配置和 IP 统计由 Kotlin/JS 适配器调用。

用实际 payload 11 在 Windows 本机启动独立代理，通过其生成的 CA 验证 HTTPS：
GitHub 首页曾重试后返回 `ECONNRESET`，耗时约 22.6 秒；
同轮 API 请求约 0.5 秒返回 200。分别访问 GitHub 的三个预设 IP，
观察到只有一个及时返回 200，其余地址无响应，且稍后各地址的连通性发生变化。
因此不能将一次成功或失败等同于所有网络环境的结论。

本次确认并修复的是现有请求恢复链路的两个缺口：

1. 无显式重试规则时只重试一次。三个候选中前两个失败，会在尝试第三个之前结束。
2. 测速只验证 TCP 连通。异步测速可再次发布 TLS/实际请求已经失败的地址，
   原请求没有独立排除记录，后续尝试可能继续选中它。

最初 Node 版本的可用记录没有同期、同网对照，不能据此断定超时由 Kotlin
迁移本身引入。诊断时曾提前加载测速模块导致旧 hostname map 未绑定，
纠正诊断加载顺序后异常消失，没有把该诊断副作用作为产品缺陷修复。

## 改动

- 为普通自定义 DNS 请求记录本次请求失败的 IP；测速存活项、按需探测、
  DNS 缓存和最终 lookup 回调均遵守排除记录。
- 根据已知、去重的候选地址数量决定默认重试额度，最多重试 3 次。
  计数包括已经从 `DynamicChoice.backupList` 移除的当前地址和已失败地址。
- 候选耗尽时保留最后的连接错误，不再次惩罚同一地址或重新建立相同连接。
- 显式重试次数继续生效；已有请求体缓冲、客户端取消和 POST 重放限制继续生效。
- ECH 继续使用其原有候选与握手恢复逻辑。
- 新补丁通过 `kotlin_payload.py` 严格、幂等地进入实际 Node zip。
  本机两份 payload 已更新；浏览器解压版本从 11 升至 12。

## 验证

- 修改前新增的两个候选切换回归均失败；修改后通过。
- Node 全套 13 个测试文件：702 项通过，零失败、零跳过。
  包括真实 Kotlin IP 选择器和预设 DNS 缓存、两个 TLS 黑洞后切换第三个地址、
  测速结果竞争、显式次数限制、最大次数、取消、流式响应和 POST 不重放。
- Python 打包：7 项通过；实际 zip 重复更新成功，无重复模块。
- Release 构建通过；浏览器 JVM：215 项通过，零失败、零跳过。
- 本机通过实际代理读取 GitHub 首页、Trending、API、Raw 文件、
  `github.githubassets.com/favicons/favicon.svg` 和 Google HK 搜索，均为 200。
  页面响应完整读取；耗时约 0.27–2.2 秒。首次资产探测用了错误路径并返回 404，
  已改为实际 favicon 路径验证。
- 在独立测试进程中，仅把 GitHub 候选设置为两个无监听的回环地址，
  再接当时可用的真实 GitHub IP，并关闭测速；完整首页返回 200，
  `DS-Retry: 2`，约 0.84 秒。此配置只存在于忽略的测试目录，未写入产品默认值。
  更早一次固定的真实 IP 在复测时已不可达，未将该失败计为通过。
- 核对 Release APK 内 zip 与浏览器 assets 一致，新候选模块随包发布。

本机日志、受控进程和网络探测资料保存在忽略的 `port/.run/timeout-fix/`。
这项修复提升可用候选之间的恢复能力，仍需要网络中至少有一个可达上游。
